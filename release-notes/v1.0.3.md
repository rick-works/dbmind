# v1.0.3

> ClickHouse 的「行数上限」与「总数」两个坑一起填掉 —— 这版之后，表数据浏览与 SQL 执行都能正常出数与出总数

发布日期：2026-10-09
类型：修订版（缺陷修复，不含破坏性变更）

## ClickHouse

- **查询不再被「行数上限」误杀**：ClickHouse 的 JDBC 驱动会把 `setMaxRows(n)` 下推成
  **服务端硬限制** `max_result_rows=n`，而服务端默认 `result_overflow_mode=throw` ——
  结果一旦超过 n，整条 SQL 直接失败（`Code: 396 TOO_MANY_ROWS_OR_BYTES`），
  而不是我们想要的「截断 + 提示」。实测：表里 226 行、上限取 201（分页 200 条/页 + 1）
  就报 `max rows: 201.00, current rows: 226.00`。
  受影响的不只是大表：**表数据浏览（默认 200 条/页）与 SQL 执行（默认 2000 行）都会踩到**，
  一张两千多行的表点开就是「SQL 执行失败」。
  现在 ClickHouse 不再下推这个上限，改由客户端按上限截断，超出部分照常显示「已截断」提示 ——
  与 MySQL / Doris / SQL Server 等其它类型的口径一致。
- **同根因的乱码报错一并消失**：服务端在结果流中途抛错时，驱动会把异常包当数据读，
  抛出 `Failed to read boolean value, expect 0 (false) or 1 (true) but we got: 105`
  这类完全看不出原因的异常。上限不再下推后，同一条查询不再出现该报错。
- **总数（基数）不再固定显示 -1**：异步计数在取「计数结果」时只认整数
  （`as_i64()`），而 ClickHouse 的 `count(*)` 回来是**浮点**（`t=real v=2377550.0`），
  取不出来就等于「统计不出」—— 派生表计数与裸 FROM 直数这两条主路双双失败，
  接着退到 CTE（ClickHouse 不认 `with t(c0,c1) as (…)` 这种显式列名写法），
  最后退到二分探测，2.3M 行要 ~44 次往返，被 10 秒预算掐断 ⇒ 界面永远没有总数
  （表现为「总数统计中…」一闪而过、之后什么都不显示）。
  现在整数 / 浮点 / 字符串三种形态都认，与「左侧树上表行数」「质量规则违规数」同一取值口径。

## 编辑器

- **选中片段点「格式化」报 `t is not a function` 修复**：函数里写了 `const t = selTextOf(ed)`，
  把 i18n 的 `t()` 遮蔽了，紧接着 `t('sqlq.formattedSelection')` 就成了「拿字符串当函数调」。
  受同一写法影响的另外 4 处一并修好：`大写 / 小写 / 单行` 转换、
  `复制为 IN 列表`、`复制为单行`（右键菜单与快捷键各一处）。
- **关键字排版「前换行」不再多断一行**：sql-formatter 的 `reservedClauses` 角色除「前换行」外
  还会把该子句的内容整体挪到下一行并缩进（`FROM\n  users u`），于是标签写着「前换行」、
  实际效果却是「前后各换行」。现在关键字独占一行时会把紧随其后那行接回来：
  `FROM users u`。「前换行 + 缩进」「前后各换行」「后换行」「后换行 + 缩进」四种行为保持不变。
