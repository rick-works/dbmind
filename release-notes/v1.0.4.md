# v1.0.4

> 后台任务不再「永远停在收尾」—— 卡住会被**如实报出来**，而不是无限期挂着

发布日期：2026-10-09
类型：修订版（缺陷修复，不含破坏性变更）

## 数据传输

- **修掉「任务永远停在后台收尾」**：真机现象是任务跑了 21 分钟，界面提示
  「任务仍在后台收尾，已允许关闭窗口」，关掉窗口、点停止都没用 —— 刷新回来它还在。
  进程侧一看：宿主 Java 进程 **0% CPU、一条数据库连接都没有**，也就是说它不是在慢慢跑，
  而是卡在一处永远不返回的等待上。
- **根因**：`cancel()` 只是一个标志位，工作体要在**分页 / 分批之间**才查得到它。一旦工作体
  卡在某个等待上（最典型：网络切换、对端掉线之后），这个检查点永远走不到，任务就永远
  停在 `running`，前端只能一直轮询。
- **修法（真实截止时间，而不是启发式猜）**：
  - 数据库调用这一层**本来就有硬截止时间** —— 内核发给宿主的是 `timeoutMs + 2s`，超时即
    `QueryTimeout`；用户取消还会经 `Statement.cancel()` 打到驱动。
  - 缺的是**流水线内部的交接**：读侧交出刚读到的一页、写侧取走一批、收尾等协程结束、
    多对象并发等槽位。这些 `send().await` / `handle.await` / `acquire().await` 原先都没有
    截止时间。现在它们统一带 660 秒的截止时间（比单次数据库调用的上限 600 秒再宽一点，
    所以正常的慢不会被误杀 —— 正常的慢只会慢在**调用**上，不会慢在"没人来取数据"上）。
  - 超时后任务以**具体原因**结束，例如
    「写入侧 11 分钟没有取走数据，判定下游已停止（连接可能已断开）」，而不是笼统地"卡住"。
- **兜底看门狗**：万一某条路径仍无任何进展（新写的循环、别的任务类型、我们自己的锁等待），
  30 分钟后强制结束并落 `error`，日志里会写明「这条路径缺少截止时间，请把本行反馈给开发」
  —— 它同时是保险与「该修哪里」的探针。已写入的部分保留，不回滚。
