# 发版说明模板（只说更新了什么 + 安装包表格）

> 用法：跑完 `node scripts/release.mjs <版本> <级别> <日期>` 之后，照这个骨架写
> `release-notes/v<版本>.md` 的**要点**；然后一条命令同步**四处**：
>
> ```
> node scripts/sync-release-notes.mjs v<版本>
> ```
>
> 它会同步：① Release 正文（**仓库里这份文件就是正文**）；② 官网版本区；
> ③ 应用「关于」页中文要点；④ 应用「关于」页英文要点（取自同目录的 `en-notes.json`）。
> 要点之外的标题、安装包表格、「最新」标记、条数都由它统一生成，手写时只写要点即可。
>
> **正文里只放两样东西**：① 这一版改了什么（`## 更新说明`）；② 安装包表格（`## 安装包`，
> 哪个文件适合谁、多大）。不放发布日期、类型标签、分节的实现解释、Linux 安装说明、升级提示
> —— 页面上左侧就是版本号、下面就是资产列表，这些要么重复、要么读者不关心。
>
> 新增版本要做的两件事：① 写中文要点（本文件）；② 在 `en-notes.json` 里补该版本的英文要点
> （条数与中文一致；缺了脚本会点名提醒）。然后跑一次同步脚本即可。

## 更新说明

> 这个标题由 `node scripts/sync-release-notes.mjs <版本>` 补上（和下面的表格一起），
> 手写时**只写要点**即可。要点用无序列表（`-`），不加序号。

- 一句话说清第一件事
- 一句话说清第二件事
- 一句话说清第三件事

## 要点这部分怎么写

1. **只列更新内容**：2~5 条，每条一行；不用小标题，不写日期、不写"修订版/新增功能"这类标签。
2. **一句话说完**：开场白一律不要（"本次更新"、"我们优化了…"）。
3. **用户视角**：说行为与结果，不说实现 —— 写"点关闭不再没反应"，别写"补了 ACL 权限声明"。
4. **短的优先**：要点部分一两屏读完最好。
5. 确实值得补充的细节（例如 Linux 依赖），写进 README，不塞进 Release。

## 渲染器支持什么（应用内的更新弹窗也用它）

标题、段落、粗体、斜体、行内代码、无序/有序列表、引用块、分割线、表格、代码块都正常。

**不支持**（写了会退化成纯文本）：图片、原始 HTML、任务列表、嵌套列表。

## 两条沿用约定

1. **重要的放最前面**：应用内的更新弹窗只显示开头一段，超出的会折叠成「查看完整更新说明」。
2. **校验值别写进正文**：SHA256 放成 Release 资产，正文里不放哈希。
