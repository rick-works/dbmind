修复 SQL Server「Windows 集成认证」不生效（选了它照样拿 user/sa 去登）

现象（实测）：SQL Server 新建数据源，认证方式选「Windows 集成验证」，测试连接报
  [DBMIND-CONN-0003] 连接失败: 用户 'sa' 登录失败
即仍然是 SQL 认证，用户名用的是界面里留着的 sa。

根因（整条链路都没把认证方式当回事）：
- 前端表单里有 authType（sqlserver / windows），也会跟着保存请求发过来；
- 但 conn.rs 组装 extra 时只收 params / environment / env / note，
  **authType 被直接丢掉** —— 保存后再打开又变回 SQL 认证，
  界面上的选择等于只影响了一个"给人看的" URL 预览；
- 更关键的是宿主侧：JDBC URL 由 YAML 的 urlTemplate 渲染，
  模板里不可能写死 integratedSecurity（同一类型还要支持 SQL 认证），
  而渲染函数也从没按认证方式加过任何东西 —— 所以永远是 SQL 认证 + 用户名口令。

改动（四处，都在"该知道这件事"的地方）：
1. conn.rs：authType 存进 extra（与 environment/env/note 同一个约定）
2. shape.rs：读回来（原来那一行是硬编码的空串），新增 EXTRA_AUTH_TYPE 常量
3. agent.rs：新增 is_windows_auth(config)；render_jdbc_url 在
   SQL Server + Windows 认证时补上
   integratedSecurity=true;authenticationScheme=JavaKerberos
   选 JavaKerberos 而不是 NTLM：走 Kerberos 票据，不需要 mssql-jdbc 那套
   平台原生 DLL（mssql-jdbc_auth-*.dll），纯 Java 就能跑
4. agent_driver.rs：Windows 认证时只把主体名（user@REALM）给宿主，
   **不给口令** —— 带上口令反而会把驱动拉回 SQL 认证

兼容性：没存过 authType 的老连接、以及默认的 SQL 认证，行为与以前**一字不差**
（新增断言专门守这一条）。

验证：
- 单测：SQL Server + windows → URL 含 integratedSecurity=true 与
  authenticationScheme=JavaKerberos；改成 sqlserver / 去掉 extra → URL 不含它
- cargo test -p dbmind-core 全绿（含既有 H2 / PostgreSQL 的 URL 断言）
